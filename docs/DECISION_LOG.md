# BooE 설계 의사결정 기록 (Decision Log)

기능별로 **"어떤 문제가 있었고 → 어떤 선택지가 제안됐고 → 어떤 흐름으로 무엇을 골랐는지"**를 정리한 문서입니다.

> **출처와 한계**
> 이 문서는 개발 과정에서 남긴 작업 메모(Claude Code 메모리), 커밋 이력, 현재 코드를 근거로 재구성했습니다. 대화 원문이 남아 있지 않으므로 다음 기준으로 구분합니다.
> - **선택 사유가 메모에 기록된 경우**에만 "사유"를 적었습니다.
> - 기록이 없으면 `(사유 기록 없음)`으로 표시했습니다. 추측으로 채우지 않았습니다.
> - "제안"은 Claude가 낸 선택지, "결정"은 개발자가 고른 답입니다.

## 1. 공공데이터 동/호 조회 — 병렬화와 API 전환

**문제 ①: 대단지 조회가 느림.** 건축물대장 API는 페이지 단위로만 응답합니다. 직렬로 페이지를 넘기면 17,000건 규모 단지에서 약 50초가 걸렸습니다.

| 제안 | 내용 |
|---|---|
| A | 직렬 유지 + 캐시로만 해결 |
| B | WebClient 비동기 병렬 페이지 호출 (동시성·딜레이 튜닝) |

**결정: B.** 동시성 30, 딜레이 50ms를 임계점 탐색으로 정해 **50초에서 11초로 단축**(커밋 `26efa6a`).

**문제 ②: 병렬화의 전제 자체가 틀렸음 (2026-06-14 발견).** 리스트를 전유공용면적 API로 만들고 있었습니다. 이 API는 세대마다 전유 1행에 공용 N행을 함께 내려줍니다. 5천 세대 단지 하나가 **46,436행**이었습니다. 반면 전유부 API는 **5,273행**으로 8.8배 적었습니다.

| 제안 | 내용 |
|---|---|
| A | 기존 API 유지, 병렬화를 더 튜닝 |
| B | 리스트는 전유부 API(동·호·층만), 면적은 사용자가 세대를 고른 뒤 **단건 조회** |

**결정: B.** `POST /contracts/unit-area`를 신설했습니다. 응답은 value(원본)와 label(표시용)로 분리했습니다.

라운드트립 검증 중 두 가지 규칙을 확인했습니다.
- 한글 동·호는 직접 URL 인코딩해야 합니다. WebClient가 `EncodingMode.NONE`이라 인코딩하지 않으면 400이 납니다.
- 단일동 건물은 dongNm이 공백(" ")으로 저장돼 있습니다. 이 경우 파라미터를 아예 생략해야 조회됩니다.

**후속 판단 — 정직성:** 이 발견으로 "대량 병렬 최적화" 성과 서사가 약해진다는 점을 인정하기로 했습니다. 처음부터 맞는 API를 썼다면 데이터가 8.8배 작았기 때문입니다. 이력서에 쓸 때 "46,000/17,000건" 프레이밍은 과장이므로 솔직하게 다루기로 했습니다.

## 2. 컨트롤러의 block() vs Mono 반환

**문제:** `getPropertyInfo`가 `Mono`를 반환할 때 403이 났던 일이 있어 `.block()`으로 우회했습니다. 그런데 `.block()`은 톰캣 워커 스레드를 외부 API 응답까지 붙잡아 둡니다.

**흐름:**
1. 처음 메모에는 "Mono 반환 = 403이니 `.block()` 사용"이 규칙으로 남았습니다.
2. 코드를 재검토해 보니 진단이 부정확했습니다. Spring Security 6은 ASYNC dispatch에서 필터 체인을 다시 돌리지 않습니다. 비즈니스 로직은 `SecurityContextHolder`를 읽지 않습니다. 이미 `getSelectableUnits`가 Mono로 정상 동작하고 있었습니다. 403의 진짜 원인은 재현되지 않았습니다.
3. 제안은 Mono 반환으로 되돌리고, 안전망으로 `JwtAuthenticationFilter.shouldNotFilterAsyncDispatch()`를 `false`로 두는 것이었습니다.

**결정:** Mono 반환 + ASYNC dispatch에서 토큰 재검증. 이전 규칙은 **정정**으로 기록했습니다.

**함께 정한 규칙:** 비즈니스 로직은 `SecurityContextHolder`를 직접 읽지 않습니다. 컨트롤러에서 `@AuthenticationPrincipal`로 받아 인자로 넘깁니다.

## 4. 회원가입·본인인증 정책

### 4-1. 본인인증 시점
| 제안 | 내용 |
|---|---|
| A | 가입 후 계약서 작성 시점에 본인인증 |
| B | **본인인증을 가입 게이트로** — 인증 안 하면 가입 불가 |

**결정: B.** 사유: 계약서 도메인이라 본인 식별이 핵심입니다. A를 택하면 "가입했지만 미인증" 상태가 생겨 가드 로직이 곳곳에 필요해집니다. 두 방안을 검토한 뒤 B로 정했습니다.

### 4-2. 소셜 로그인 가입 방식
**결정:** 2단계로 정했습니다.
1. 카카오 토큰을 검증합니다. 기존 회원이면 로그인, 신규면 임시 가입 토큰(Redis TTL 10분)을 발급합니다.
2. 추가 정보와 본인인증을 거쳐 가입을 완료합니다.

### 4-3. 카카오에서 받은 email·name 사용 여부 (2026-04-30)
**결정: 사용하지 않습니다.** 카카오 인증은 OauthConnection 저장 용도로만 씁니다. 사유: 카카오 이메일은 부계정인 경우가 많아 영구값으로 부적합하고, 이름은 본인인증으로 어차피 덮어씁니다. 사용자가 직접 입력한 값이 더 신뢰할 만합니다.

### 4-4. CI 중복(이미 가입한 사람) 처리
| 제안 | 내용 |
|---|---|
| ① | 차단 — "이미 가입된 회원입니다" |
| ② | 자동 계정 연결 |
| ③ | 본인 확인 후 연결 |

**결정: ①로 시작하고, 요청이 많아지면 ③을 추가합니다.** ②는 소셜 계정 탈취 시 기존 계정까지 넘어가는 위험 때문에 채택하지 않았습니다.

### 4-5. CI/DI 저장 구조
**결정:** `MemberIdentityVerification` 별도 테이블에 저장합니다. `ci_hash`(HMAC-SHA256, UNIQUE, 중복 검색용)와 AES-256 암호화 원본을 둡니다. 사유: 민감정보 격리, 감사 로그 분리, 법적 보관 정책이 다르다는 점.

### 4-6. 본인인증 업체 (2026-04-27)
| 제안 | 내용 |
|---|---|
| NICE평가정보 | 점유율 1위, 레퍼런스 많음 |
| 토스 본인인증 | 토스 앱 의존성 |

**결정: NICE.** 사유: 토스는 토스 앱 의존성이 우려됐습니다. 사업자등록이 필요해서, 그 전까지 phoneNum은 **사용자 직접 입력**으로 받는 임시안을 쓰기로 했습니다.

### 4-7. 작업 순서
**결정:** OAuth 구현을 먼저 하고, 본인인증 통합(⑤)은 보류했습니다. 사유: NICE 가입 심사라는 외부 의존이 있어 기다리는 동안 할 수 있는 일을 먼저 하기 위해서입니다.

**미확정으로 남은 것:**
- 인증 결과 전달은 Redis 토큰(A)을 권장했지만 최종 확정은 하지 않았습니다.
- 기존 PhoneVerification 제거(A)도 권장만 하고 확정하지 않았습니다.

## 6. 결제 — 금액 검증

**문제:** 클라이언트가 보낸 `amount`·`orderId`를 토스 confirm에 그대로 전달하고 있었습니다. 그래서 금액을 3중으로 검증하는 코드가 붙어 있었습니다.

| 제안 | 내용 |
|---|---|
| A | 클라값 전달 유지 + 검증 강화 |
| B | 주문 생성 시 Redis에 `{orderId, amount}`를 저장하고, **토스에는 서버 기억값으로 confirm** |

**결정: B.** 클라이언트가 금액을 변조하면 토스 측 결제 인증값과 일치 검증에서 자연스럽게 차단됩니다. `validateAmount`와 `validateConfirmedAmount`는 dead code가 되어 **제거**했습니다.

**연관 결정:** "결제 금액 3중 검증"은 이력서 어필 항목에서 **제외**했습니다. 사유: 잘못된 패턴이었기 때문에 필요했던 검증일 뿐이고, 정상 패턴으로 바꾸면 불필요해집니다(§16 참고).

## 7. 결제 — 중복 승인 방지(멱등성)

**문제:** 중복 클릭, 재시도, 동시 요청으로 같은 `paymentKey`에 confirm이 두 번 갈 수 있었습니다.

**결정 (2026-05-19):** 이중 안전망을 두었습니다.
- Redis `SETNX` + TTL 60초로 `paymentKey`별 락을 겁니다. 일반적인 동시 요청을 막습니다.
- `payment.payment_key` UNIQUE 제약을 둡니다. 락 만료, 크래시, Redis 장애에 대비한 폴백입니다.

**검증:** 동시 50요청에 성공 1, 차단 49, 토스 confirm 1회(`PaymentIdempotencyConcurrencyTest`, 실 MySQL+Redis). 이 테스트를 작성하다가 §11의 스키마 드리프트를 발견했습니다.

## 8. 결제 — 트랜잭션 범위와 orphan 결제

**문제 ①:** `confirmPayment` 전체가 하나의 `@Transactional`이었습니다. 토스 호출(외부 IO)과 FCM 동안 DB 커넥션을 점유해, 동시 결제가 몰리면 커넥션 풀이 고갈될 위험이 있었습니다.

**문제 ②:** 토스가 청구에 성공한 뒤 우리 측 처리가 실패하면, 롤백 때문에 기록이 사라집니다. 그러면 "청구만 살아남은" orphan이 생깁니다.

**제안된 옵션:** 자동 보상 cancel, PENDING 정리 스케줄러, Toss Webhook.

**결정 (2026-05-22):**
- 클래스 레벨 `@Transactional`을 제거하고 오케스트레이션 형태로 바꿨습니다.
- `PaymentRecordService`를 별도 빈으로 분리했습니다. 흐름은 `[TX1: PENDING insert] → 토스 호출(트랜잭션 밖) → [TX2: APPROVE + 계약 상태 + Redis 정리]`입니다.
- **`REQUIRES_NEW`는 쓰지 않았습니다.** 사유: 데드락이 우려됐습니다. 기본 `REQUIRED`에 별도 빈 호출로 짧은 트랜잭션을 만들었습니다.
- `confirmWithCompensation`의 try/catch로 토스 호출 이후 실패를 감지하면 자동으로 cancel합니다.
- 보상 cancel 자체가 실패하면 `FAILED` + `CANCEL_FAILED` 이벤트로 기록합니다.

**인정한 한계:** 보상 자체 실패와 서버 크래시는 try/catch로 못 잡습니다. 그래서 §10 스케줄러를 1순위 후속 과제로 정했습니다.

## 9. 결제 — 상태 모델과 이력

**결정 (2026-05-22):**
- `REFUNDED` 상태를 **폐기**하고 `CANCELED`로 통합했습니다. 환불, 시스템 취소, 스케줄러 정리가 모두 `payment.cancel(시각)`을 거칩니다. `refundedAt` 대신 `canceled_at`을 둡니다.
  - 사유: 환불 흐름이 하나뿐이라 도메인 단순화가 낫다고 봤습니다. 사유 구분이 필요해지면 이벤트 테이블로 확장합니다.
- 상태별 시각, 사유, actor, payload를 본체 컬럼으로 늘리지 않고 **`PaymentEvent` 시계열 테이블**로 분리했습니다(`CREATED`, `APPROVED`, `CANCEL_SUCCEEDED`, `CANCEL_FAILED`, `RECONCILED`, `ABANDONED`, `AMOUNT_MISMATCH` / actor `SYSTEM`, `USER`, `ADMIN`, `SCHEDULER`).
  - 사유: 본체를 단순하게 유지하고, "이 결제가 어떻게 흘러왔는지" 추적과 감사가 가능하게 하기 위해서입니다. 트랜잭션 안에서 INSERT 1건이 추가되는 비용은 외부 IO에 비하면 무시할 수준입니다.

## 10. 결제 — PENDING 정리 스케줄러(Reconciliation)

**문제:** §8의 미커버 케이스(보상 실패, 크래시) 때문에 PENDING이 영구히 남을 수 있었습니다.

**후속 과제 우선순위 제안(당시):** [A] PENDING 스케줄러 → [B] 알람 → [C] PDF 재시도 → [D] 비동기 분리 → [E] 환불 락 → [F] timeout → [G] Webhook → [H] Rate limit

**결정:** [A]부터 진행했습니다(커밋 `2d63e3b`).
- `fixedDelay` 5분, `PENDING AND created_at < now - 5분`인 건을 토스 조회 API로 실제 상태를 확인합니다.
  - `DONE` + 검증 일치 → APPROVE로 복구
  - `CANCELED`, `ABORTED`, `EXPIRED` → CANCELED
  - 불일치 → ABANDONED
  - 진행 중이거나 조회 실패 → 다음 회차에 다시 시도
- 건별 try/catch로 한 건의 실패가 배치 전체를 멈추지 않게 했습니다. 조회 클라이언트는 throw 대신 null을 반환합니다.
- `fixedDelay`로 자기 자신과의 중복 실행을 피했습니다. 다중 인스턴스가 되면 ShedLock을 도입합니다.
- 효과: orphan을 **최대 10분 안에** 정정합니다(임계 5분 + 주기 5분).

**함께 판단한 것:** Circuit Breaker는 결제에 **부적합**하다고 봤습니다. 결제에는 fallback이라는 개념이 맞지 않기 때문입니다.

## 11. 스키마 드리프트 사고

**문제 (2026-05-27):** 멱등성 테스트 중 `payment` INSERT가 `Data truncated for column 'status'`로 실패했습니다. 테스트 버그가 아니라 **실제 결제도 깨지는 상태**였습니다.

**원인 분석 흐름:**
1. 처음에는 Hibernate가 `@Enumerated(STRING)`을 VARCHAR로 만든다고 생각했습니다. 이건 **오인**이었습니다.
2. 확인해 보니 Hibernate 6은 MySQL 네이티브 `enum(...)` 컬럼을 만듭니다. 그리고 `ddl-auto=update`는 기존 enum 값 목록을 ALTER하지 않습니다.
3. 결과적으로 컬럼에 옛 상수(`DONE`, `REFUNDED`)가 굳어 있었습니다.

| 제안 | 내용 |
|---|---|
| A | `ALTER`로 컬럼을 VARCHAR나 새 enum으로 수정 |
| B | DB를 DROP하고 재생성 (payment 0건이라 무손실) |
| C | Flyway/Liquibase 도입 (근본 해결) |

**결정:** 중간에 A(VARCHAR ALTER)를 시도했다가 **최종적으로 B**를 택했습니다. 시드는 `LoadTestSeedRunner`로 다시 만들었습니다. C는 후속 과제로 남겼습니다.

**남은 리스크:** enum 상수를 바꿀 때마다 같은 일이 재발합니다. 그래서 Flyway 도입을 서비스화 P0로 올렸습니다(SERVICE_READINESS P0-2).

## 12. PDF 생성 — 측정 → 폰트 캐싱 → 비동기 바운드 풀

이 기능은 **"추측 대신 측정으로 결정한다"**는 흐름이 가장 분명했던 작업입니다.

### 12-1. 측정으로 문제 정의 (2026-05-27)
- 단일 PDF 생성에 60~80ms가 걸렸고, **96%가 OpenHTMLtoPDF 렌더와 폰트 처리**였습니다. Thymeleaf는 약 3ms뿐이었습니다.
- 처리량은 동시성 c≈4에서 초당 약 45건으로 정체됐습니다(CPU 바운드).
- **c=32에서 OOM**이 났습니다. 부하가 높아지면 느려지는 게 아니라 터졌습니다.
- 결제 응답 82.7ms 중 **PDF가 51ms(62%)**를 차지했습니다.

### 12-2. 첫 가설: 폰트 캐싱 → 일부 빗나감
- 제안: `malgun.ttf`(약 22MB)를 매번 읽지 말고 `byte[]`로 1회 로드하면 시간과 메모리가 모두 줄어들 것이라고 봤습니다.
- 결과:
  - latency는 **38% 단축**됐습니다(78.9 → 48.8ms).
  - **메모리는 거의 그대로**였습니다(41.4 → 41.2MB/장).
  - 처리량이 오르면서 c=16의 OOM이 0건에서 6건으로 **오히려 늘었습니다**.
- 결정: 가설이 빗나갔음을 기록하고 **정정**했습니다. 캐싱은 "시간만 줄이는 quick win"으로 두고, 바운드 풀이 더 필요하다는 결론을 냈습니다.

### 12-3. 메모리 측정으로 풀 크기 산정
- 1장당 working set은 약 60MB였고, 메모리 누수는 없었습니다(retainedΔ=0).
- 공식: `N = (가용 힙 − 기존 워크로드 − 마진) / 60MB`
- 로컬 -Xmx 512MB 기준으로 CPU 정점과 힙 천장이 **모두 c=4**였습니다.

### 12-4. 비동기 분리 결정 (2026-05-29)
| 제안 | 내용 |
|---|---|
| A | `@Async` + 전용 바운드 풀 |
| B | Redis Stream + Consumer Group (더 견고) |
| C | 이벤트 발행 + 워커 + 지수 백오프 재시도 |

**결정: A부터.** 풀 구성은 N=4, 큐 100, `AbortPolicy`입니다. 무제한 큐는 새로운 형태의 OOM을 만든다는 점에서 바운드 큐를 택했습니다.
- `PdfJobDataLoader`를 `readOnly` 트랜잭션으로 분리했습니다. lazy 로딩을 피하고 커넥션을 즉시 반환하기 위해서입니다.
- 결과:
  - 결제 응답이 **82.7ms에서 29.8ms**로 줄었습니다.
  - 동시 32 결제에서 **OOM 7건 → 0건, PDF 유실 7건 → 0건**이 됐습니다.
- **측정 축을 분리**하기로 했습니다. 응답 latency 축과 PDF 병목(OOM) 축은 다른 문제이므로 각각 따로 검증했습니다.

### 12-5. JFR로 원인 확정
- CPU의 약 80%가 폰트 파싱과 서브셋팅이었습니다. 파일 I/O가 없어도 PDFBox가 매 호출마다 CMAP과 glyph를 재파싱합니다. 그래서 `byte[]` 캐싱으로는 메모리가 줄지 않았던 것입니다.
- GC가 시간의 약 30%를 차지했고, Full GC도 발생했습니다. 이 점에서 풀로 동시성을 제한하는 것이 GC 측면에서도 정당화됐습니다.
- 다음 카드는 PDFBox를 직접 써서 `PDType0Font` 객체를 캐싱하는 것입니다. **트래픽을 보고 결정**하기로 보류했습니다.

### 12-6. 의도적으로 미룬 것
- 클라이언트가 받는 pdfPath가 "곧 생길 경로"로 의미가 바뀐 점에 대한 처리(404 재시도나 FCM 대기)
- Reconciliation을 PDF 누락 감지와 재처리로 확장
- 이 두 가지는 서비스화 P0-5로 올렸습니다.

## 16. 작업 방식 자체에 대한 결정

### 16-1. 코드 컨벤션
- 메서드는 최대 15줄, 가능하면 10줄로 씁니다. 단일 책임(SRP)과 SOLID를 지킵니다.

- 사유: 실무 기준의 가독성과 유지보수성을 최우선으로 두기 때문입니다.

### 16-2. 이력서·PAAR 톤
- 제안된 어필 후보 중 **"표준 패턴을 적용했을 뿐인 작업"은 제외**했습니다. 예: 결제 3중 검증, JWT 구현, Security 적용.
- 남긴 것은 **정량 결과와 비표준 판단**이 있는 작업입니다. 예: 병렬화 50→11초, ASYNC dispatch 처리, single-flight, reconciliation, PDF OOM 7→0.
- 사유: "그게 표준 패턴 아닌가요?"라는 면접 질문 한 번에 깨지는 과장을 가장 경계하기 때문입니다.
- 같은 원칙으로 §1의 API 전환 발견 후 병렬화 서사를 **스스로 약화**시켰습니다.

## 17. 결정 패턴 요약

여러 결정에서 반복적으로 드러난 판단 흐름입니다.

1. **측정이 먼저, 가설은 그 다음.** PDF(§12), 병렬화(§1), 멱등성(§7) 모두 수치로 문제를 정의한 뒤 해결책을 골랐습니다. 가설이 빗나가면(폰트 캐싱) 숨기지 않고 정정했습니다.
2. **단순하고 표준적인 해법을 우선하고, 근거가 생기면 확장합니다.** `@Async`를 Redis Stream보다 먼저, 스케줄러를 Webhook보다 먼저, 단일 인스턴스 single-flight, 기본 `REQUIRED` 트랜잭션.
3. **이중 안전망.** 일반 경로 가드(Redis 락, try/catch 보상)와 최후 방어선(DB UNIQUE, reconciliation 스케줄러)을 분리했습니다.
4. **외부 의존은 기다리지 않고 병렬로 진행합니다.** NICE 심사 대기 중 OAuth 진행, 사업자등록 전 임시안.
5. **보안상 애매하면 보수적으로 고릅니다.** CI 중복 시 자동 연결 대신 차단, 카카오 프로필 미사용, 주민번호 최소 수집.
6. **잘못된 기록은 덮어쓰지 않고 "정정"으로 남깁니다.** block() 규칙(§2), VARCHAR 오인(§11), 폰트 캐싱 가설(§12).
